# 全幅拼贴幕墙 — 性能与适配实测报告

> 数据来源：本仓库 `apps/desktop/src/test/mosaic-layout.test.ts` 的 Vitest 实测输出，
> 以及 `scripts/capture-screenshots.mjs` 在真实运行的 `vite preview` + Edge 无头实例上的
> DOM 探测（`docs/design/screenshots/viewport-probe.json`）。
> 本报告只记录**实际测得**的数字，不以 DOM 数量或单次耗时宣称「60 FPS」。

## 1. 布局引擎耗时与首屏挂载量

测试机：本机 Windows，Node 22.22.2，**Vitest 5.1.0**，`canvasWidth = 1920`
（v0.3.1 重新实测，2026-11-08；个人视频已改为保留真实画幅，画布高度随之变化）。
`firstScreenMounted` 按「1080px 视口 + 上下各 700px overscan」模拟可见区间统计。
数据由 `stress(n)` 复制演示条目生成唯一 Media ID，不使用重复对象引用。

| 条目数 | 一次完整布局耗时 | 画布高度 | 首屏挂载磁贴 | 不同宽度值数量 |
|---:|---:|---:|---:|---:|
| 40 | 0.29 ms | 3,452 px | 23 | 34 |
| 200 | 1.44 ms | 14,498 px | 25 | 123 |
| 500 | 4.27 ms | 36,216 px | 25 | 237 |
| 1000 | 13.82 ms | 71,208 px | 25 | 336 |

> 单次运行值；同一台机器多次运行会有 2–6 倍波动（JIT / 负载），
> 分布数据见第 3 节的中位数与 P95。**数字一律来自测试输出，不手工挑选。**

结论：

- 布局耗时随条目数近似线性增长，1000 条约 14 ms，远低于一帧预算。
- **首屏挂载量与总条目数无关**（23–25 个），因为渲染层按绝对 y 坐标裁剪，
  而不是把 1000 个节点全部挂到 DOM 上；这是真正的可见区域虚拟化，
  旧版「每批追加 24 个」只是增量渲染，不属于虚拟化。
- 不同宽度值数量持续上升（40 条 34 种 → 1000 条 336 种），
  说明尺寸是连续计算而非固定六档。

## 2. 四种分辨率 / 画布适配

`canvasWidth` 取 1280 / 1920 / 2560 / 3440，对应 1280×720、1920×1080、
2560×1440、3440×1440 四种窗口。每项都跑了完整不变量检查（零重叠 + 左右/底部边界）。

| 画布宽 | 画布高 | 磁贴数 | 最大/最小面积比 | 右边界溢出 | 重叠 |
|---:|---:|---:|---:|:---:|:---:|
| 1280 | 3,113 | 52 | 15.0× | 无 | 0 |
| 1920 | 4,206 | 52 | 13.8× | 无 | 0 |
| 2560 | 5,147 | 52 | 13.5× | 无 | 0 |
| 3440 | 4,138 | 52 | 21.9× | 无 | 0 |

超宽屏（3440）上面积反差扩大到 21.9×，说明尺寸层次没有被拉平；
所有分辨率均无水平溢出、无磁贴重叠。v0.3.1 起**个人视频保留真实画幅**
（16:9 / 4:3 / 21:9 不再被映射成其他比例），因此画布高度与 v0.3.0 不同——
这是修复生效的证据，不是布局退化。

## 3. 1000 条完整不变量验证与耗时分布

任务书 6.1 要求 1000 条数据跑**完整**的零重叠与边界检查（不是抽查）。
`src/test/mosaic-invariants.test.ts` 用 Sweep Line 全量比对所有磁贴对，
并与旧的两两比较 `validateMosaic` 交叉验证。

覆盖：40 / 200 / 500 / 1000 条 × 1280 / 1920 / 2560 / 3440 画布宽度；
其中 1000 条在 1280 与 1920 下执行完整重叠检查。

| 不变量 | 结果 |
|---|---|
| 无重复 Media ID | 通过 |
| x ≥ 0、y ≥ 0 | 通过 |
| width > 0、height > 0、均为有限值 | 通过 |
| 不超出画布右边界 / 底部 | 通过 |
| 任意两个磁贴不重叠（全量 Sweep Line） | **0 对重叠** |
| 自定义顺序在 1000 条布局中不被破坏 | 通过 |
| 连续尺寸仍然成立（1000 条时不同宽度值 336 种） | 通过 |

耗时分布（1000 条 / 1920px / 连续 7 轮，由测试 `console.warn` 真实输出）：

| 阶段 | 中位数 | P95 | 最小 | 最大 |
|---|---:|---:|---:|---:|
| 布局计算 | 6.80 ms | 9.16 ms | 6.19 ms | 9.16 ms |
| Sweep Line 重叠检测 | 1.03 ms | 1.11 ms | 0.98 ms | 1.11 ms |

**未做逐帧 FPS 采样**：上表是布局与验证耗时，不是滚动帧率，不据此宣称任何 FPS。
DOM 数量与内存变化也未采集，见第 6 节。


## 4. Windows 显示缩放（逻辑视口模拟）

Windows 125% 缩放时物理像素不变、**CSS 视口变窄**（1600 物理 → 1280 CSS）。
因此用等比例缩小的 `--window-size` 模拟不同缩放下的逻辑视口，对真实运行实例
做 `--dump-dom` 探测，读取 `.mosaic` 的 `data-canvas-width` / `data-mounted`。

| 模拟缩放 | 逻辑视口 | 实测画布宽 | 首屏挂载 |
|---:|---|---:|---:|
| 100% | 1600×1000 | 1570 px | 15 |
| 125% | 1280×800 | 1250 px | 15 |
| 150% | 1067×667 | 1037 px | 17 |
| 200% | 800×500 | 770 px | 20 |

四档均随视口变窄重新编排，画布宽始终等于可用 CSS 宽度，未出现溢出或挤压；
窄视口下磁贴变小、首屏可容纳更多（15 → 20），符合连续尺寸的预期。
数据来源：`docs/design/screenshots/viewport-probe.json`（每次截图都会重算并覆盖）。

> **必须说明的边界**：这是逻辑视口模拟，**不是**在真实 Windows
> 「显示设置 → 缩放」下验证。Edge 无头模式的 `--force-device-scale-factor`
> 实测只改变输出位图密度、不改变 CSS 视口宽（四档均为 1570px），
> 因此本报告不把它当作 DPI 验证。真实 Windows 缩放下的观感需人工在桌面端确认。

CSS 侧使用 `clamp()` 连续尺寸、`object-fit: cover` 裁切、绝对定位 + transform，
不依赖固定像素列宽；布局引擎以 `clientWidth`（CSS 像素）为输入。
`.page-scroll` 保持 `overflow-x: hidden`，幕墙页左右 padding 为 0，不产生水平滚动条。

## 5. 已落实的性能策略

| 策略 | 实现位置 |
|---|---|
| 图片懒加载 | `LazyImage` + `useInView`（rootMargin 700px）+ `loading="lazy"` / `decoding="async"` |
| 缩略图多尺寸缓存 | `useArtwork` 按 `box.width` 选 sm/md/lg/xl；WebDemoBridge 用 `getArtwork` 内存缓存 |
| 可见区域渲染 | `MasonryWall` 按 `box.y` 与滚动区间过滤，容器高度固定为 `canvasHeight` |
| 避免不必要重渲染 | `MediaTile` 用 `memo`；布局 `useMemo` 只依赖 items / customOrder / canvasWidth / focal |
| 避免频繁重算 | ResizeObserver 回调合并到一帧；滚动区间按 160px 台阶量化后才 setState |
| 拖拽期间不重排 | dragover 只更新高亮 id，布局 memo 不失效；drop 时才写 customOrder |
| 尊重减少动态效果 | `@media (prefers-reduced-motion: reduce)` 关闭 slot / art / tile 过渡 |
| 资源释放 | 卸载磁贴时 `img` 随 DOM 移除；`useArtwork` 的 effect 有 active 标记取消异步更新 |

## 6. 尚未实测的部分（如实标注）

- **真实帧率（FPS）未采集**：本报告只有布局计算与重叠检测的耗时分布，
  没有做逐帧采样，因此**不提供任何 FPS 数字**，也不把布局耗时冒充滚动帧率。
- **DOM 数量**：只在截图脚本的 DOM 探测里记录了首屏挂载磁贴数（15–20 个，
  见 `viewport-probe.json`），没有做 1000 条滚动过程中的 DOM 数量曲线。
- **内存变化**：未做长时间播放/滚动的内存曲线采集。
- 1000 条压力测试用的是程序合成的条目（复用 48 张演示封面），
  不是 1000 个真实媒体文件；真实扫描与刮削性能需 Tauri 桌面端接通后另测。
